## 2) OUTDATED PRACTICES / ROT RISK (12-month horizon)

- **Hard dependency on Node’s global WebSocket (Node 22+) for CDP**
  - `apps/api/src/application/runtime/cdp/cdp-connection.ts` assumes global `WebSocket`. This is relatively new and has had behavioral differences across Node minors. If you need Node 20 LTS support (common in ops), this breaks.
  - Fix: vendor a minimal WS client or explicitly pin Node version across all packages and CI; document as hard requirement (you partly do in root `package.json` engines >=20.10, but code comment says Node >=22).

- **PowerShell-driven DPAPI and engine bootstrap is brittle**
  - SecretStore DPAPI uses `powershell.exe -Command ...` (`apps/api/src/application/secrets/secret-store.ts`).
  - Fury launch bootstrap uses a generated `.ps1` with `ExecutionPolicy Bypass` (`apps/api/src/application/runtime/fury-core.runtime.ts`).
  - Rot risks:
    - PS 5.1 vs PS 7 differences
    - Enterprise policies blocking `ExecutionPolicy Bypass`
    - AV/EDR heuristics (you already hit `-EncodedCommand` problems; `-File` can still be flagged later)
  - Fix: move to a native Node addon or a tiny signed helper executable for DPAPI + handle inheritance; reduce dependence on PS scripting.

- **SQLite schema migrations are raw SQL strings embedded in code**
  - `apps/api/src/infrastructure/database.ts` uses inline SQL strings; OK early, but as schema grows, this becomes hard to test/validate and easy to break on partial deploys.
  - Fix: add migration tests + checksum, and/or use a migration framework or at least file-based migrations.

- **Using `execFileSync("tar", ...)` for extraction assumes OS tar presence**
  - `apps/api/src/application/engine/engine-installer.ts` shells out to `tar`.
  - On Windows, `tar` availability varies (bsdtar in recent Windows, but not guaranteed in stripped environments).
  - Fix: embed a decompressor (even minimal) or ship a known-good tar binary with installer tooling; or enforce presence with a preflight check + clearer doc.

## 3) SECURITY GAPS (severity-rated)

### P0 / High

- **SSE endpoint is cross-origin readable (`Access-Control-Allow-Origin: *`)**
  - File: `apps/api/src/http/events.routes.ts`
  - Mechanism: SSE replies include `access-control-allow-origin: "*"`. If the API token is *not* set (common for loopback local tools), **any website the user visits** can open `EventSource("http://127.0.0.1:50325/events")` and read live lifecycle events (profile IDs, run IDs, URLs in tab.opened detail, startpage failures, etc.).
  - Even if a token *is* set, browsers do send Authorization headers only if caller sets them (EventSource cannot set headers); that means token-protected SSE becomes unusable from browser dashboard unless same-origin without token—but the wildcard CORS still invites probing.
  - Suggested fix:
    - Remove `Access-Control-Allow-Origin` entirely for loopback.
    - If you need browser dashboard access, rely on same-origin policy (serve dashboard from same origin) and do not enable cross-origin.
    - Consider CSRF-like “loopback abuse” mitigations: check `Origin` header, require token always, or randomize port by default.

- **Proxy passwords may be stored in plaintext SQLite in some modes**
  - Files:
    - `apps/api/src/application/proxies/proxy.repository.ts` stores `password` column.
    - `apps/api/src/application/proxies/proxy.service.ts` only uses SecretStore if present; otherwise password stays in DB.
  - While you try to always create SecretStore in `main.ts`, tests/other contexts can run without it and silently persist plaintext. This is a real footgun if non-Windows devs set `QUEUEPILOT_SECRET_STORE=plaintext` (explicit) but still: operationally, “plaintext secrets mode” is dangerous.
  - Suggested fix: make SecretStore mandatory in production builds; refuse to start without secure store unless an explicit `--insecure-allow-plaintext-secrets` flag is set (and log loudly).

### P1 / Medium

- **Plugins/JYL execute arbitrary local code in-process (expected) but HTTP endpoints expand blast radius**
  - Files: `apps/api/src/application/jyl/jyl-registry.ts`, `apps/api/src/http/jyl.routes.ts`, `apps/api/src/application/plugins/plugin-registry.ts`
  - Mechanism: operator-installed `.mjs` can expose `/jyl/endpoint/*` routes. If API is bound beyond loopback (config allows `SPECTRA_HOST`), this becomes remote RCE-as-a-service for anyone with the bearer token (or without it if token unset).
  - Suggested fix: enforce loopback-only unless token is set; and even with token, consider a separate “enable remote HTTP exposure” setting. Optionally disable JYL endpoints unless explicitly enabled.

- **Cookie “thinger” can exfiltrate full cookie values over HTTP**
  - File: `apps/api/src/application/cookies/cookie-thinger.ts` + `apps/api/src/http/cookies.routes.ts`
  - Mechanism: `GET /profiles/:id/cookies` returns cookie values in JSON. With local malware or any web-to-loopback exploitation (see SSE issue class), this is direct session theft.
  - Suggested fix: require API token for cookie routes regardless of global setting; add a “redacted list mode” default and a separate “export raw values” endpoint gated behind explicit operator confirmation.

- **Zip extraction: no size limits / zip bomb protection**
  - File: `apps/api/src/application/extensions/zip.ts`
  - You prevent zip-slip (`safeJoin`) and skip `__MACOSX`, good. But there’s no cap on number of entries, total uncompressed size, or per-file size. A malicious zip could exhaust disk/memory.
  - Suggested fix: enforce max entries, max total extracted bytes, and max per-file size.

### P2 / Low

- **Engine config JSON written to disk in profile dir**
  - File: `apps/api/src/application/runtime/fury-core.runtime.ts` writes `fury-config.json`.
  - Depending on what persona config includes over time, this could leak sensitive persona characteristics or future secrets. Right now it’s fingerprint fields + webrtc policy.
  - Suggested fix: keep as-is if it’s non-secret, but document; or write config to temp and hand handle (same pattern as oscrypt key) if it ever gains sensitive fields.

If other security areas are clean: core crypto for bundles is reasonable (AES-256-GCM + PBKDF2, uniform error) in `apps/api/src/application/bundles/session-bundle.ts`.

## 4) CODE QUALITY (staff-review blockers / maintainability)

- **The API auth hook is overly simplistic and fragile**
  - File: `apps/api/src/app.ts`
  - Mechanism: compares `req.headers.authorization` string equality. No trimming, no case-insensitive scheme parsing, no support for multiple tokens, no expiration, no constant-time compare.
  - Fix: parse `Authorization` robustly, support token rotation list, and use timing-safe equality.

- **In-memory state makes post-restart behavior permanently degraded**
  - Tabs, sessions, JYL stores are in-memory only. Adopted runs are second-class (no tab ops, bundle ops, autofill).
  - Files: `BrowserLifecycleService` + `TabRegistry` + bundle/autofill logic.
  - Fix: implement “reattach” strategy:
    - store enough run metadata to reconnect to CDP after restart
    - rebuild tab registry from `Target.getTargets` + your partition mapping strategy (or accept “no partition recovery” but at least allow non-partitioned ops)

- **Some “best effort swallow errors” could hide real corruption**
  - Examples:
    - `Target.detachFromTarget` calls are `.catch(() => {})` in many places (autofill, cookies, attestation). That’s OK for shutdown hygiene, but you have no structured logging, so debugging hard failures is harder.
  - Fix: add debug-level logs (even if logger disabled by default).

- **Dashboard performs N+1 calls per running profile**
  - File: `apps/api/src/dashboard/app.js` in `renderProfileGrid()`:
    - For each running profile it calls `/profiles/:id/drift` and `/profiles/:id/tabs`.
  - This will fall over with dozens/hundreds of running profiles.
  - Fix: add batch endpoints (e.g., `/profiles/running/summary`) or include drift/tab counts in `/profiles` response.

- **Package-lock is oddly located**
  - File: `.github/workflows/package-lock.json`
  - This is nonstandard and will confuse tooling and security scanners. It also appears truncated in the snippet; if this is a real lockfile, it should live at repo root.
  - Fix: move lockfile to root and ensure CI uses it; remove stray lock under `.github/workflows`.
