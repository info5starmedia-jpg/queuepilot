# Research: local AI assistants that answer questions about their own app state

**Date:** 2026-11-21 · **Task 5, Step 1** · Method: web search + direct fetch of primary docs, no code changes.

Context: QueuePilot's P9 agent runs on a local 7B-class model (qwen2.5:7b-instruct via Ollama) with ~21 function-calling tools over app state (profiles, proxies, warmups, plugins, engine). The owner asked "how many proxies do I have listed" and got an error; the fix already shipped (`app_overview` aggregate tool + a capability-listing system prompt, commit `921bdaa`) is checked against the sources below.

## Sources

1. **[Ollama tool calling docs](https://docs.ollama.com/capabilities/tool-calling)** — official. Confirms `stream: true` works with tools (a dedicated "Tool calling with streaming" section, gather `tool_calls` across chunks then feed results back); arguments arrive as an **object**, never a JSON string (`call.function.arguments` used directly) — our provider's `normaliseArgs()` JSON-string fallback is defensive, not something Ollama's own docs say is needed; parallel tool calls are a first-class case (one assistant turn, several `tool_calls[].index`, one `tool` reply per call); the "use only the first call" shortcut is explicitly "only recommended for models which only return a single tool call" — not true for every model. Schema examples use short one-line `description`s per tool and per property; the Python client can derive a tool schema from a plain function's docstring.
2. **[Anthropic — Building effective agents](https://www.anthropic.com/research/building-effective-agents)** — official. Core advice: start with the simplest solution (direct tool calls in a loop) and add complexity only when simple patterns demonstrably fail; avoid frameworks that hide what's actually being sent to the model. QueuePilot's agent loop (one system prompt + tool catalog + a step cap) already follows this — there's no planner, no multi-agent graph, no vector store.
3. **[Anthropic — Writing tools for agents](https://www.anthropic.com/research/writing-tools-for-agents)** — official. The key reframe: **a tool is not an API endpoint** — it needs a description written for a model, not a developer. Its two most actionable points: (a) read the model's own transcripts to see which tool it picked and why — wrong-tool-picked errors are a description problem, not a bigger-model problem; (b) track tool-call counts and errors per tool as a metric, because a spike in "invalid parameters" on one tool usually means its description or schema is unclear, not that the model is incapable.
4. **[Small Models, Big Tasks (arXiv 2504.19277)](https://arxiv.org/html/2504.19277v1)** — peer-reviewed-adjacent empirical study. Finding that directly bears on us: tool-use accuracy depends far more on **strict schema adherence and argument correctness** than on parameter count — when given explicit schemas and a validator in front of execution, small models can match larger ones. QueuePilot already validates every tool call's arguments with zod before running it (agent.service.ts), which is exactly the mitigation this paper credits.
5. **[ToolScan (arXiv 2411.13547)](https://arxiv.org/pdf/2411.13547)** and the **[Mingbird harness paper (arXiv 2610.02001)](https://arxiv.org/pdf/2610.02001)** — both document the concrete 7B-class failure modes: ignoring a `required` argument that's explicit in the schema; repeating an identical tool call when the model is unsure what to do next (Mingbird calls this out specifically for 2–9B models); emitting a tool call as prose/quasi-JSON that a strict parser then discards rather than a well-formed `tool_calls` entry. None of these are "wrong tool" errors — they're argument and call-pattern errors, which matches what we actually saw in the live reproduction (the model picked the right tool both times; the gap was that reaching the answer took 2 reads instead of 1, and nothing told it "no" / "limits" / "capabilities" in advance).
6. **[DigitalOcean — RAG vs MCP/tools](https://www.digitalocean.com/community/tutorials/engineers-guide-rag-vs-mcp-llms)** and a second practitioner piece — consistent with each other: retrieval (RAG) fits static, slowly-changing documents (policies, how-to text); live tool calls fit anything that is "the current X" — counts, running state, account info. Proxy/profile counts are exactly the second category, so a vector store or cached snapshot would be the wrong tool here; a cheap, always-fresh aggregate tool call is the right one, and is what we built.

## What this means for us (ranked)

Already done (checked against the research above, each is independently supported by at least one source):
1. **One aggregate `app_overview` tool** for "how many / what do I have" instead of forcing the model to chain several granular reads — directly the pattern source 6 recommends for live-state questions, and it removes the chance of the wrong-tool or multi-step failure modes in sources 4–5.
2. **A system prompt that enumerates capabilities and limits in plain language** — addresses the exact "I can't do that" / invented-answer failure class; not explicitly named in the sources, but follows directly from source 2's "simplest thing that works" principle and source 3's point that behavior problems are usually a description problem, extended from tool descriptions to the top-level system prompt.
3. **Zod-validated tool arguments before execution** — the single most evidence-backed mitigation in the small-model literature (source 4), already in place in `agent.service.ts`.
4. **Plain-language unreachable-model error** instead of a raw "fetch failed" — not from these sources specifically, but a basic instance of "the model can't fix what it can't see," i.e. failures should be legible to the operator, not just the model.
5. **Temperature 0 and tool results fed back into the loop** — matches Ollama's own documented agent-loop pattern (source 1: keep calling until no more `tool_calls`, deterministic-leaning for an operator command that should do the same thing twice).

Not yet done — ranked by value if this keeps mattering:
1. **Read the actual transcripts of real failures** (source 3's top recommendation). We could not reproduce the owner's literal error on this machine; the next time it recurs, capturing the raw model output (not just the tool-call outcome) would show directly whether it's a parsing, argument, or prompt-adherence issue rather than requiring a second diagnosis from scratch.
2. **Per-tool call/error counters** (source 3). Cheap to add to the existing `actions.jsonl` append-only log — group by tool name and outcome, surface in `/agent/status` or a small admin view. Would catch a flaky tool early instead of after an owner report.
3. **A rescue-with-feedback retry for malformed tool calls** (source 5's Mingbird finding, for 2–9B models specifically) — if a response fails to parse as a valid tool call, feed the parse error back to the model once before giving up, rather than only validating the arguments of calls that already parsed. Not implemented; would need a change to the provider/loop boundary, out of scope for the immediate fix.
4. **Tool descriptions mentioning units/"no" cases explicitly** (source 1's note on single-vs-parallel call handling, source 3's "stop it from adding a year" example) — worth revisiting if any tool shows a pattern of wrong arguments in the action log once item 2 exists.

## Where sources disagree or are version-dependent

- Ollama's streaming+tools support is stated plainly by the official docs (source 1) as of this read (2026-11-21), but at least one third-party client doc (an Elixir wrapper, and an older Spring AI page referencing version 0.2.8) claims Ollama does **not** support tool use with streaming. This is very likely stale/client-specific rather than a current Ollama limitation — the official page we fetched directly shows a dedicated streaming+tools example — but it's worth re-checking against whatever Ollama version ships if this ever becomes a live bug report.
- The "single-call shortcut" ("use only the first call") is explicitly scoped by Ollama's own docs to "models which only return a single tool call" — it is not a general simplification, and assuming it for every model would silently drop tool calls on models that do return several.
- One blog source (not included above — a dev.to post benchmarking a 3B model) claims sub-7B models "effectively cannot" do tool calling at all; this conflicts with the peer-reviewed-adjacent survey (source 4) and the ToolScan benchmark (source 5), which both show 7B models succeeding a majority of the time with the right scaffolding (schema validation, explicit required-argument descriptions). Treated as an outlier and not used above.
